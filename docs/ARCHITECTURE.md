# Turing AI architecture

## System overview

Turing AI is a set of thin native apps around one shared Swift package, plus an independent Kotlin port:

```text
Apps/iOS (Mosaic-iOS) ────┐
Apps/macOS (Mosaic-macOS) ├─ Packages/MosaicCore ─ Domain + Persistence + Providers + Connections + Scheduling + Sync + UI
Apps/ShareExtension ──────┘   (the extension compiles in only Persistence/SharedInbox.swift; no Keychain or main-library access)

Apps/Watch (Turing-Watch) ─── Packages/TuringVoice (Foundation-only voice/chat protocols; no MosaicCore dependency)

Apps/Android ─ :core (pure Kotlin) ← :data (Room, Keystore, repositories) ← :app (Compose UI)
```

- **iOS, iPadOS and macOS** are separate SwiftUI application targets (`Mosaic-iOS`, `Mosaic-macOS`) defined in `project.yml` and generated with XcodeGen. They stay separate so background behavior, menus, entitlements and platform integrations can evolve independently; shared views adapt through SwiftUI navigation rather than Mac Catalyst. Both link `MosaicCore` and include `Brand/ProviderLogos.xcassets`.
- **watchOS** (`Turing-Watch`, in `Apps/Watch`) is a single-target Watch app embedded in the iOS app. It depends only on `Packages/TuringVoice`, never on MosaicCore's SwiftData/UI graph. See [WATCH.md](WATCH.md).
- **Share Extension** (`Turing-Share`, in `Apps/ShareExtension`) is a minimal UIKit extension with App Group access only; it stages shared items for the main app.
- **Android** (`Apps/Android`) is a native Kotlin/Jetpack Compose port with `:core`, `:data` and `:app` Gradle modules that mirrors the Swift feature set and limits. See [ANDROID.md](ANDROID.md).

### Layers in MosaicCore

`Packages/MosaicCore/Sources/MosaicCore` is organized by responsibility:

- `Domain`: provider, chat, memory, project, retrieval, document, and schedule types plus source-field limits.
- `Persistence`: SwiftData source records and versioned schemas, a separate rebuildable semantic index, document extraction/OCR, backup codec, and Keychain access.
- `Providers`: request builders, same-origin networking, streaming decoders, model-catalog parsers, and provider-specific adapters.
- `Connections`: direct vendor APIs, hosted MCP and native Apple stores, device Keychain credentials, public-client OAuth, account-bound access, reviewed actions and durable activity receipts. See [CONNECTIONS.md](CONNECTIONS.md) and [GOOGLE-CONNECTIONS.md](GOOGLE-CONNECTIONS.md).
- `Scheduling`: recurrence math, foreground task execution and local notifications.
- `Sync`: the private-iCloud library manifest, transport, merge and conflict handling.
- `UI`: adaptive SwiftUI workspace (Root, Chat, Memory, Projects, Providers, Settings, Tasks, Design).
- `Resources`: the bundled `ProviderModels.json` and `ModelPrices.json` catalogs, the `TuringBrand` asset catalog, and third-party notices.

Provider clients receive plain immutable request snapshots. They do not query SwiftData or Keychain directly. The application layer resolves a Keychain secret, builds the visible memory context, and then starts a stream. This keeps secrets and storage concerns out of parsers and makes provider behavior testable with URL stubs.

## Provider catalog and transports

ProviderKind identifies 50 curated presets while ProviderProfile owns their category, endpoint, suggestions, request limits, authentication, capabilities, catalog shape, and visual fallback. Provider identity is not a transport: most hosted and local presets reuse the OpenAI Chat Completions/Embeddings wire implementation; OpenAI Responses, Anthropic Messages, Gemini content generation and batch embeddings, native Qwen/Cohere embeddings, and nonstandard model catalogs use focused adapters.

Capabilities are fail-closed. Chat selectors and scheduled tasks include only chat-capable records, embedding profiles include only embedding-capable records, and Gemini Live is exposed only on Google. Model discovery is used only where the preset has a compatible, documented catalog shape. Anthropic, Gemini, Cohere, and Featherless request up to 1,000 records per page and Fireworks up to 200, following opaque cursors where supported for at most 20 pages/10,000 unique IDs while rejecting cursor cycles and overlarge payloads. xAI uses its language-model endpoint; Mistral's `completion_chat`, Together's typed array, Fireworks' `conversationConfig`, Featherless's server-side chat capability filter, Chutes's top-level output modalities, Hugging Face/OpenRouter/Poe architecture output modalities, AI/ML API's type and endpoint fields, Vercel's model type, Tencent's positive text-family list, and Baidu's text-output type/modality keep offline, embedding, image, and other non-chat records out of chat selection. AI/ML API's exact official model catalog is public, so its editor labels that operation as catalog reachability, does not attach a credential to the request, and explicitly leaves both the key and selected model unverified; a custom AI/ML-compatible catalog retains the normal authenticated connection-test behavior. OpenAI, Meta Model API, Groq, SambaNova, NVIDIA NIM, Nebius, Baseten, Scaleway, DigitalOcean, Novita AI, Microsoft Foundry, and Amazon Bedrock keep automatic model discovery disabled where the hosted compatible catalog is mixed, lacks a positive chat discriminator, is unavailable, or is tied to a different endpoint surface. Untyped OpenAI-compatible listings from custom and local runtimes likewise stay manual; only LM Studio's native typed catalog is auto-discovered locally, and only records explicitly marked `llm` enter the chat selector. Exact model or deployment IDs remain editable for every provider. Every identifier is limited to 1,024 UTF-8 bytes, control characters are rejected, and retained unique identifiers share a 4 MiB budget. Curated suggestions bootstrap the editor, discovered account models are merged into that list, and the exact ID always remains editable.

Embedding requests carry an explicit query/document purpose. Official Qwen endpoints use the native DashScope text API and official Cohere endpoints use `/v2/embed`; Voyage, Jina, NVIDIA, and Gemini translate the same intent to their respective wire fields or prefixes while custom compatible hosts retain their standard envelope. NVIDIA GTE/GTR identifiers omit the unsupported `input_type`. Each profile remains a separate vector space. The client preserves input order while splitting Qwen 3.7 batches at 20 items and older/unknown Qwen batches at 10, Baidu batches at 16 (`tao-8k` at one), and all other app batches at 64 items. Every response and the combined split result must retain the expected count and one nonzero dimension before anything can be persisted. Local/custom profiles without a verified model default require explicit input, except LM Studio profiles can also use its typed native catalog.

Streaming completion is successful only after a terminal event. OpenAI-compatible `stop` and `normal` finish reasons are terminal even when a compatible host omits `[DONE]`; trailing usage is retained before clean EOF or the sentinel closes the stream. Length/content-filter/tool stops, Anthropic non-text stop reasons, Gemini prompt blocks and non-`STOP` finish reasons, and OpenAI incomplete responses surface as failures with the provider reason; Responses API refusal deltas remain visible assistant text instead of becoming an empty answer. A request-local MiniMax normalizer converts its documented cumulative `delta.content` snapshots into UTF-8-safe incremental deltas and fails closed on a non-monotonic snapshot, preventing duplicated persisted output across chat, automation, and compaction consumers. Streaming requests use a 15-minute idle deadline and finite 24-hour resource ceiling for long research jobs. Provider text is cumulatively bounded at 512 KiB and control events at 4,096, while the transport-to-consumer channel is lossless; Gemini's cumulative per-chunk usage metadata is coalesced to the latest counters and emitted before completion so a long valid stream cannot exhaust the control-event budget. Chat persistence checkpoints at 8 KiB or 250 ms instead of saving SwiftData for every token.

## Gemini Live transcription

Live transcription is a separate provider-independent input path, not a chat dialect:

1. The conversation chooses an enabled Google record whose resolved destination is exactly Google's HTTPS Gemini origin, then resolves the endpoint-bound key from Keychain.
2. GeminiLiveTranscriptionClient opens the fixed dedicated WebSocket, rejects redirects, sends a bounded SMART transcription setup for gemini-3.5-transcribe-live, and waits for setupComplete.
3. LiveMicrophoneAudioSource requests system permission, captures through AVAudioEngine, and statefully downmixes/resamples hardware input into bounded 100 ms PCM16 mono 16 kHz chunks with finite backpressure.
4. Interim hypotheses replace one another only in the rendered composer. LiveTranscriptAssembler commits final segments deterministically; the draft's 512 KiB source limit is checked before every UI update.
5. A normal stop tears down capture, sends audioStreamEnd, and drains for up to 12 seconds. A later final transcript or turn-complete event confirms the result; at the deadline, silence/no pending hypothesis is distinguished from a genuinely unresolved interim transcript, and only the latter produces a partial-result warning. Backgrounding or leaving the conversation enters this same graceful path; explicit cancellation remains immediate.
6. Provider `GoAway` is reported as a provider-requested close rather than being mislabeled as a time limit. A separate local 585-second event begins graceful finalization before the 600-second hard limit.
7. On iOS, a balanced short-lived background execution assertion protects the stop-to-final-result drain. Expiration ends the assertion first, cancels the session, flushes finalized draft text, and reports that unresolved interim words may be missing; macOS does not enter this path.
8. The operation coordinator prevents chat generation, conversation deletion, restore, or another process-wide microphone session from racing the same conversation. Embedding-profile deletion owns a process-wide exclusive operation lease through source deletion and full cache cleanup, so an in-flight request, import, or indexing job cannot recreate a vector for a removed profile. The chat provider sees only finalized draft text after an explicit Send.

## Bundled model discovery

`Resources/ProviderModels.json` is a dated offline suggestion catalog with all 50 provider coverage records, exact model IDs, official sources, and compatibility notes. `BundledProviderModelCatalog` loads it once through `Bundle.module`; it never grants account access or enables catalog additions. Existing saved IDs remain visible even when removed from suggestions. Provider defaults retain preferred verified IDs, while each stored connection keeps its saved model.

Empty preset model IDs are never inserted into the enabled set; otherwise sorting selects the empty sentinel before an explicitly added model and keeps Save disabled. Large disabled bundled inventories are not copied into SwiftData: persist enabled IDs, saved/custom/discovered IDs, customized limits, and a legacy-model marker. The marker ensures an entirely disabled catalog cannot fall back to an enabled legacy choice. Refresh retains the last successful inventory on failure and respects the existing endpoint/credential cancellation gate. Featherless uses its documented conversational filter and up to 50 bounded pages; model and byte budgets remain enforced. AIML endpoint types, Gemini dedicated media/agent families, and OpenRouter batch routes require explicit compatibility filtering.

## Optional recall reranking

`RecallRerankStage` plugs into `SemanticMemoryCoordinator.validatedContext`. When the user enables a reranker, the first stage is widened to 20 candidates (`HybridMemoryRetriever.withLimits`), `RerankProviderClient` scores them (Cohere `/v2/rerank`; DeepInfra's native inference route; Jina, Voyage and `<base>/rerank` hosts share one request shape; raw logits are squashed to probabilities), and `HybridMemoryRetriever.select(rankedBy:)` applies the usual item, container and size limits to the reranker's order. Reranker scores replace the blended relevance rather than joining it: feeding them through the 0.42-weight lexical blend lost most of the gain on the benchmark. Scores are cached per request so a stale-source retry never pays twice, a 12-second timeout and every error fall back to the ordinary ranking with a warning, and the stage never runs for the Smart memory path. The stage reads `RecallRerankerSettings` (UserDefaults, off by default) and the provider is resolved on the main context, so no schema change is involved.

## Request context budgeting

Every interactive chat and foreground scheduled request passes through a deterministic provider-independent planner after pinned and retrieved context is assembled:

1. Bound the system prompt and each complete message at one token per UTF-8 byte plus protocol framing. This intentionally overestimates normal prose and remains useful for dense code, JSON, random identifiers, emoji, and unknown provider tokenizers.
2. Use the context-window and maximum-output limits saved with the selected provider/model. Curated identifiers with documentation-backed metadata receive exact model defaults; unknown hosted IDs use a conservative 32,768/4,096 fallback, while unknown local-runtime and custom IDs use 8,192/2,048. Legacy records without saved limits resolve through that same exact-model-or-conservative policy. The window and output cap are user-editable; the estimated input budget and 512–2,048 token safety margin are derived read-only values. Saved overrides belong to the exact provider/model sidecar. Switching models never transfers another model’s limits. A legacy provider’s overrides carry only to its previously selected model when creating its managed catalog.
3. Send the full history while it remains below the compaction high-water mark. At roughly 72% of the safe input budget, select only a contiguous oldest prefix of completed turns for one bounded summary request, targeting roughly 55% utilization.
4. Always preserve the current user message and two newest completed prior turns verbatim. Never character-truncate a message or delete/replace a raw source row.
5. If the protected current/system/recent content cannot fit, fail visibly before the chat-generation request instead of silently damaging the prompt.
6. Before answer streaming begins, append a bounded request-context event containing the source boundary, raw suffix IDs, token limits, artifact references, metrics, and warnings. Summary coverage comes from the referenced immutable compaction artifact; still-omitted IDs are derived from the authoritative transcript boundary. The UI can therefore reconstruct the exact raw-included/summary-covered/same-chat-recalled/still-omitted partition without persisting an ever-growing copy in every answer.

### Rolling conversation compaction

Compaction is application-owned rather than provider-owned:

1. `ConversationCompactionPlanner` measures the summary instructions, JSON envelope, optional prior summary, raw source batch, provider output reserve, and safety margin before allowing an extra request. A large legacy chat gets at most one safe batch per send instead of an oversized or unbounded burst of paid calls.
2. The app captures one immutable provider/model/endpoint/key binding and uses the generic `AIChatRequest`/`AIProviderClient` stream for both compaction and the final response. The core path does not depend on OpenAI opaque state, Anthropic-specific tools, or provider-native structured-output modes.
3. Transcript data is JSON encoded beneath fixed app instructions. The model must return a small versioned JSON summary. The app requires a terminal provider event, a nonempty bounded result, the supported schema, and allowed item kinds; partial or malformed output is never persisted as active context.
4. The app computes ordered coverage itself and fingerprints length-prefixed message ID, role, complete status, and exact UTF-8 content with SHA-256. Before every use—and again after an asynchronous summary call—the snapshot must match the same conversation and exact authoritative raw prefix. Edits, deletion, reordering, corruption, or a cross-chat pointer fail closed; appending newer turns remains valid.
5. A valid summary is stored once as an immutable portable compaction artifact with provider/model/full normalized endpoint, usage, response ID, lineage, estimates, warnings, and only the new coverage delta. A small per-conversation head points to the active artifact. Switching the chat provider does not rewrite or invalidate the summary.
6. The final prompt carries the summary as an older synthetic user/assistant context pair, never as privileged system instructions. The envelope labels it untrusted historical data, and newer raw messages and corrections follow it and take precedence.
7. A validated result must create real savings twice: the complete request must shrink, and the summary must be smaller than the exact context it replaces—raw prefix for initial/rebuild, or prior summary plus new raw delta for an extension. A verbose provider response that only appears smaller because unrelated middle turns were omitted is rejected.
8. Every extra attempt is visible as an append-only request-context event: generating is committed before opening the provider stream, and generated, failed, or cancelled is appended rather than overwriting the earlier evidence. Reuse references an existing artifact without claiming another provider call. If the process dies after generating was committed, opening that conversation first inspects only the newest bounded audit window (at most 64 events and 2 MiB of payload); it reads canonical chat history only when that preflight finds a newest-per-answer generating attempt, then appends one failed terminal event exactly once. The recovery holds a source-operation lease across preflight, canonical read, and terminal commit, so whole-store replacement cannot interleave generations. Crash-orphaned assistant rows receive the same once-per-generation launch repair; when active operations drain, a fresh idempotent rescan also catches a terminal persistence failure that happened after the initial scan. A possible provider call therefore cannot disappear from the audit trail, and ordinary chat opens do not scan complete history for recovery. Older legacy repair is left to a dedicated background scanner rather than an unbounded foreground pass. Failed output may still have incurred provider usage, and the app does not invent a currency cost when no versioned price catalog exists. User cancellation propagates before the final answer request.
9. Cross-window generation is serialized per conversation. The canonical raw rows and active snapshot are re-read before deciding, after acquiring the gate, after asynchronous summary generation, and immediately before the final provider stream. A newer snapshot prevents a sequential duplicate compaction request.
10. Once summary/recent planning is final, `SameConversationRecallPlanner` searches only completed user messages named by that plan's summarized or omitted IDs. It excludes verbatim-included IDs, uses a separate local-only quota of up to three excerpts and 4,000 characters, and places its untrusted synthetic pair after any summary but before newer raw turns. Recall never displaces the base planner's newer raw context; excerpts shrink or are omitted when unused room is insufficient, and the final byte-based estimate must still fit the same safe input budget. Normalized audits preserve whether each exact excerpt came from the summarized prefix or the unsummarized omitted middle. Restore accepts overlap with summary coverage only for a correctly labeled `.summarized` excerpt and rejects duplicate, raw-suffix, or incorrectly labeled membership.

If compaction cannot produce a valid usable summary, the existing recent-raw planner remains the explicit fallback when its protected content fits. A retry appends a new assistant attempt and receipt, preserving the failed attempt's partial output, error, provider/model provenance, and context receipt; an unchanged active summary is reused without another extra call.

## Memory and retrieval pipeline

The source of truth and the derived index are deliberately separate:

```text
Earlier-chat user messages ─┐
Pinned facts ────────────────┼─ local candidate snapshot ─ local hybrid scores ─┐
Learned topic heads ─────────┤                                                  ├─ rank fusion ─ bounded external context
Imported document text ─────┘                                                  │
                                                                                │
Embedding profile A ─ query/vector scores ──────────────────────────────────────┤
Embedding profile B ─ query/vector scores ──────────────────────────────────────┘

Active-chat summarized/omitted user messages ─ local hybrid scores ─ bounded exact historical pair
```

1. Import document source text locally. One picker batch accepts at most eight files, 50 MiB per file, and 100 MiB total; files are extracted and committed sequentially so expanded payloads are not retained for the full batch. The visible Stop action propagates cancellation through size checks, file reads, PDF page preparation, OCR, chunking, and indexing boundaries; already committed source text remains available with an honest partial-import result. PDFs use their embedded text layer when it is useful; blank, scanned, or weak-text pages are rendered within pixel limits and recognized on-device with Apple Vision. Only one selected representation is stored per page to avoid hidden-text/OCR duplication. The bounded OCR planner reserves capacity for blank pages; optional weak-text pages beyond the limit retain their embedded text and increment a visible fallback count. Every generated chunk retains its page number and whether its selected text came from OCR; this provenance is copied into request receipts and rendered recall context.
2. Before conversation planning, a dedicated SwiftData model actor resolves the target conversation's project sidecar and fetches immutable snapshots of only accessible completed user messages, active learned-topic heads, enabled document chunks, embedding profiles, and non-secret provider metadata. A project chat can read global sources plus exact same-project sources; an unassigned chat can read only global and unassigned sources. Source rows are read in bounded pages; message, document, and topic lanes stop at both their candidate-count ceiling and an 8 MiB UTF-8 payload ceiling. SwiftData model objects never cross the actor boundary. A message already consolidated as learned-topic evidence is suppressed from raw cross-chat recall, so pausing, forgetting, or correcting the head cannot be bypassed by its old source excerpt. After the final conversation plan is known, independently search only canonical completed user messages in the active chat whose IDs are summary-covered or otherwise omitted.
3. Build a 96-item semantic candidate pool with Turkish-aware lexical scoring and a deterministic character n-gram vector. Source fetch, vector-cache paging, fingerprinting, Float32 decode/encode, cosine scoring, and rank fusion run away from the main UI actor with structured cancellation checks.
4. Run up to four enabled embedding profiles in parallel. The editor prevents a fifth active profile instead of silently demoting an older model. Missing chat vectors are filled lazily; newly imported documents and profiles are backfilled in batches.
5. Keep each provider/model/base-URL vector space isolated and combine only rankings. Cosine scores below the semantic confidence threshold cannot surface an otherwise irrelevant item.
6. Diversify the external pool by source container and cap it at six excerpts and 8,000 characters. The active-chat lane has an independent three-item/4,000-character ceiling and must also fit the remaining final request budget. All recalled text is serialized as untrusted reference data, not executable instructions; newer raw active-chat turns remain later and authoritative.
7. Immediately before the chat provider call, revalidate selected source IDs/fingerprints, the target and candidate project memberships, and enabled profile/embedding-space snapshots. Then append the final normalized request event. It distinguishes exact active-chat excerpts from earlier-chat/document recall, snapshots the exact project instructions sent, and records the final estimate after recall.

### Project scope

Projects use additive `ProjectRecord` and unique deterministic `ProjectResourceBindingRecord` sidecars rather than adding columns to historical entities. One conversation, curated memory, learned topic, or document can belong to at most one project; an absent binding means personal/global according to that resource's own scope. Linked documents are project-only, while unlinked documents are available everywhere. Archived projects remain readable by their existing chats but cannot receive new assignments. Project instructions are a separate system-context layer and never overwrite `ConversationRecord.systemPrompt`.

Conversation/project assignment changes are blocked while provider, transcription, indexing, deletion, or maintenance work is active in the process. Retrieval candidates carry the target project audience through every asynchronous embedding stage and are checked against a fresh model context before vector persistence or prompt inclusion. Automatic-memory preparation similarly captures the project ID; apply rejects the result if the conversation moved and project topic keys include `project:<uuid>:<kind>:`. New project topics and their bindings commit atomically. Moving a conversation atomically rekeys and rebinds an automatic topic supported exclusively by that conversation; if its evidence spans audiences, the whole move is rejected instead of leaving a partially widened memory. Automatic topic reads query the exact global, current-conversation, and current-project partitions before applying result limits, so unrelated project volume cannot starve an eligible topic. This protects the boundary even if state changes after a provider request starts.

### Automatic durable memory

1. Only after an assistant reply is durably saved as complete, the app enqueues an idempotent formation job for that exact completed user-message boundary. The successful reply is never delayed or changed by this work. The same immutable provider/model/normalized endpoint and credential binding used for the chat is reused for one separately disclosed request; assistant text is never sent as evidence.
2. The extractor sends a JSON data envelope beneath fixed anti-injection instructions and adapts its payload and output allowance to the selected provider's saved context policy. It returns at most 12 atomic operations over a small provider-independent taxonomy. Strict JSON shape, enum/range/text limits, eligible evidence IDs, likely-secret patterns, and existing-topic targets are validated locally before any source mutation.
3. Formation uses an exact ordered content fingerprint for the source message, stores provider/model/endpoint provenance, captures the current project audience, and rechecks them after the network suspension. Existing topic snapshots include resolved project scope and form a compare-and-swap boundary, so an edit, pause, forget, project move, or competing consolidation that occurs while the provider is running wins and makes the stale result fail closed.
4. One transaction updates the current topic head and appends exact source evidence plus a semantic revision. Repeated equal values reinforce the head; explicit corrections replace only its current value; explicit forget language deactivates it. A project chat may update, reinforce, or forget a visible global head only by naming that exact topic ID; it still cannot manufacture a new global topic. A user-edited head is authoritative: implicit output cannot change it, and an explicit changed value requires its exact topic ID and high confidence. Current user text outranks curated facts, curated facts outrank learned topics, and learned topics outrank older raw excerpts.
5. The Memory library exposes the automatic-memory switch, Everywhere/project/conversation scope, active/paused/forgotten state, source excerpts, provider/model/host provenance, revision history, and recent formation-request/token activity. Topics can be corrected, paused, restored, or forgotten without a per-item approval gate. Paused, forgotten, and disabled topics are excluded before the bounded existing-topic snapshot is serialized, so they are sent neither through recall nor through a later extraction-provider request. Forgetting preserves the local audit trail; the original message remains normal history inside its original conversation.
6. A durable formation-audit start record commits before the provider stream opens. Reported token deltas and the terminal state are appended idempotently; relaunch reconciliation marks an interrupted attempt failed exactly once and never automatically repeats a call that may already have consumed credits. Pending work may continue only before a request start and while the original enabled provider identity, model, endpoint, source fingerprint, and audience still match. Failed attempts remain bounded and visible for an explicit paginated retry instead of looping and spending credits; immutable local source-loss or counter exhaustion is recorded as Not applied and is never offered for another paid retry. Deleting a provider atomically preserves dormant unfinished jobs as rejected audit history, while an actually running provider request blocks that mutation. The source deletion commits before Keychain removal; a non-secret durable cleanup tombstone distinguishes a pre-commit crash, which must preserve the live provider's key, from a post-commit crash, which is retried idempotently on the next ready launch. Conversation deletion removes scoped topics, detaches deleted evidence from revision history, preserves manually corrected global heads, deactivates unsupported automatic heads, and removes both message and topic vectors from the rebuildable cache. Archived-project chats do not enqueue work that cannot pass the audience gate.

Timeouts preserve only validated completed embedding batches for reuse. Cancellation stops CPU/network children and performs no cache write. If there is no enabled embedding profile, retrieval never opens the vector store; if every configured model is offline, the local hybrid retriever still produces a result. Vector reads are bounded to selected profiles and candidate-ID pages rather than loading the complete cache. Records are content-fingerprinted, dimension-checked, and stored in `SemanticIndex.store`; a dimension change between split provider batches fails before a result is returned. A process-wide serialized read-before-write invariant also enforces one persisted dimension for each profile and embedding-space identifier across separate retrieval and document jobs. Any mixed legacy space is treated wholly as stale until rebuilt instead of silently comparing incompatible vectors. The conversation/document database remains usable if this rebuildable cache is unavailable. Document health streams source fingerprints and vector metadata through 128-record UUID pages on model actors, computes exact per-document coverage, and never materializes the chunk corpus, vector table, or vector blobs on the UI actor. Backfill embeds at most 32 chunks per profile job and revalidates the profile, provider, model, document, and source fingerprint after every network suspension before an exact bounded cache write. A full rebuild removes active derived document vectors plus true dangling records through bounded UUID scans, keeps source text, disabled-profile caches, fifth-profile caches, and conversation vectors intact, and then pages through all enabled documents. Results finishing after a profile, provider, model, or chunk change are discarded before persistence.

## Data policy

- The main SwiftData store holds conversations, raw messages, immutable normalized request events, provider-portable compaction artifacts and active heads, pinned facts, learned-topic heads/evidence/revisions/formation jobs, imported document text/chunks, OCR/fallback page counts, embedding profile metadata, tasks, and non-secret provider metadata. New libraries use the platform-resolved Application Support directory under `Mosaic/Mosaic.store`; a successful cold-launch recovery selects a verified store under `Mosaic/StoreGenerations/<uuid>/Mosaic.store` through the atomic active-generation pointer. A recognized legacy library in the same sandbox namespace remains at its existing `default.store` URL until an explicit asynchronous relocation workflow is implemented. Each new message snapshots its provider kind so later edits to a reusable provider configuration cannot rewrite historical visual provenance; older records without a snapshot remain text-only instead of guessing a potentially incorrect logo.
- A second SwiftData store holds only rebuildable Float32 embedding vectors with a unique profile/source cache key.
- Keychain stores one API key per provider record. Provisioned builds with an Apple application identifier use the Data Protection Keychain. The explicit local ad-hoc Debug build has no authorized application identifier, so a compile-time-gated policy selects the traditional macOS file-based Keychain and omits both Data Protection and accessibility-only query attributes; Release builds without the required identity fail closed instead of silently downgrading. The backend is selected once for the process and never changes after an operation fails. Local ad-hoc items are not silently migrated into a later provisioned access group and may require explicit re-entry after a rebuild or properly signed release. New credential writes include a non-secret binding to the provider adapter and exact normalized, percent-encoded base endpoint; request snapshots must present the same binding before the key is returned. Encoded separators such as `%2F` remain distinct from `/`. A legacy raw value is never released directly: only an exact endpoint shipped before binding existed is atomically upgraded and verified by readback, while custom or changed destinations require re-entry and leave the prior item intact. Changing the provider type in the editor resets its endpoint, model, and request limits together, preventing a newly entered key from silently following the previous provider's custom host. Delete and replacement remain available after a binding mismatch, while a failed configuration transaction restores an opaque snapshot of the prior Keychain item without decoding or rebinding it.
- Chat requests go directly from the device to the selected chat host. Enabled embedding profiles separately receive the recall query and selected earlier-chat/document excerpts; the UI discloses those destinations. The exact active-chat recall lane is local-only and creates no extra embedding request. While live transcription is active, microphone chunks go only to Google's fixed Gemini Live origin; finalized text remains a local draft until Send.
- Cross-host redirects are rejected so an authorization header cannot leak to a different origin.
- The local conversation database is not described as end-to-end encrypted.
- Tinfoil currently uses its direct HTTPS compatibility API. The provider is explicitly marked as not using Tinfoil SDK attestation yet.

## Store versioning, backup, and recovery

The main conversation store is source-of-truth data. `MosaicSchemaV1` freezes the previously shipped entity layout; `MosaicSchemaV2` adds only normalized receipt, compaction-artifact/head, and backfill-progress tables; `MosaicSchemaV3` additively introduces learned-topic heads, evidence, revisions, and formation jobs; `MosaicSchemaV4` adds only project, resource-binding, and formation-audit tables; `MosaicSchemaV5` adds `ProviderModelRecord` and `ScheduledTaskModelRecord` sidecars. V1-V4 entity hashes remain unchanged and V4→V5 is a lightweight migration. A legacy connection exposes exactly its old default model until a managed catalog exists; an explicitly disabled catalog never falls back to that model. Tasks persist an exact provider/model choice separately from provider credentials. Backup extensions validate, rekey, replace and read back both sidecars. Legacy `contextReceiptData` and `compactionSnapshotData` columns remain intact for a rollback window. New writes use normalized records, reads prefer verified normalized data and fall back to legacy bytes, and a bounded idempotent backfill API can advance explicit batches without deleting a malformed or undecodable legacy blob. Moving that conversion loop to a dedicated model actor remains intentionally deferred until the normalization codec is shared as one pure implementation rather than duplicated across actors. Earlier builds may have written to Application Support's generic `default.store`. When no dedicated store exists, the app reads that file's Core Data metadata without changing its durable database or WAL content. An exact Mosaic V1/V2/V3/V4 entity set, or a superset of the original five-entity Mosaic core signature, selects the legacy URL and lets the existing migration plan make the authoritative hash/migration decision in place; an unsupported historical hash therefore fails closed instead of creating a shadow empty library. A readable store without that strong signature is treated as foreign and left untouched while a new dedicated store is created. Unreadable or malformed metadata also fails closed. Copying or relocating a potentially large live legacy database is intentionally deferred to a future explicit asynchronous workflow. App Sandbox prevents a signed macOS build from discovering a store created by an unsigned app in the process-global `~/Library/Application Support` namespace, so that case requires a future user-authorized import or transitional migration channel and is not claimed as automatic recovery.

A portable `.mosaicbackup` is a separate logical format, not a raw SQLite copy. It deterministically snapshots every base source entity plus automatic-memory topics/evidence/revisions/jobs/audits, projects and resource bindings, per-provider model catalogs/limits, per-task model selections, and opaque legacy/normalized audit bytes; records a format/minimum-reader version; limits the current in-memory envelope to 256 MiB, one record to 8 MiB, total records to 1,000,000, and a normalized request payload to 512 KiB; then verifies an SHA-256 integrity value before mutation. Project restore validation rejects missing projects/resources, duplicate or non-deterministic membership, cross-scope bindings, and project topic keys that do not match their bound project. A verified export lease first flushes pending UI changes through the same source-field validation and revision gate as normal saves. Capture scans each collection in bounded UUID/string keyset pages and applies the exact encoded-envelope byte budget plus record limits before retaining each item, so an over-limit library fails without first materializing an unbounded payload. Keychain material, app-local preferences, and the rebuildable semantic index are excluded. Import rejects duplicate IDs, malformed normalized/legacy audit data, invalid numeric bounds, missing hard references, topic/evidence scope mismatch, altered source fingerprints, and incomplete provider provenance; it rekeys provider configurations to prevent accidental local Keychain inheritance, remaps operational references, disables every restored provider until explicit review, and pauses restored automations. The candidate archive is imported and fetched back in a staging container before the user can confirm one transaction-like logical replacement in the live model context; validation failure leaves live data untouched. Snapshot capture, staging/fetch-back, live replacement, and semantic-cache deletion run through dedicated serial SwiftData model actors, so the UI actor can continue animating, announcing status, and accepting cancellation. Main-store autosave is disabled and every normal source commit passes through a process-local lease, preventing snapshot or replacement while a chat request, memory-formation job, scheduled task, provider mutation, document import, or semantic-index operation still owns records from the current store generation. Restore removes source rows in bounded keyset pages but retains rollbackable mutations until its one explicit save; the archive's 256 MiB/1,000,000-record limits bound that transaction. Restore also keeps an exact pre-commit logical compensation image when the current source generation is verified. After its first durable replacement, cancellation is no longer observed: a fresh context verifies the complete target, repairs a late foreign-context write, or commits and verifies the former library before reporting failure. If neither complete generation can be verified, a durable recovery latch survives relaunch and blocks normal reads, requests, commits, and exports; only Data & Recovery remains interactive so a later verified restore can clear the latch. Libraries above 256 MiB require a future streaming archive format rather than silently weakening the on-device memory bound.

The sidebar applies a nonblank-draft/message-existence filter before pagination and search; empty records remain available for active navigation without becoming history entries. With implicit autosave disabled, conversation drafts use a gated 900 ms debounce and flush immediately when a scene becomes inactive, enters the background, or disappears. The root workspace never materializes the full conversation or message tables on the UI actor: active and archived chats are read as independent 16-item model-actor pages, the selected chat uses an exact one-record query, and search scans title/message rows in four-record keyset batches before returning only the requested page. A selected transcript likewise keeps only its newest 16 records in a bounded live query; older rows are requested as stable 16-item keyset pages. Complete provider-facing history, same-chat recall candidates, and normalized/legacy compaction projection are prepared in four-record keyset batches on a private model actor and fail closed at either 20,000 source rows or 16 MiB of canonical message text. Supported writes and backup restore additionally cap one message at 512 KiB so a fetched page cannot defeat the aggregate guard.

Curated-memory selection scans at most 4,096 rows in four-record actor pages, retains at most 20 facts, budgets content to 12,000 characters, bounds titles, and limits both retained raw strings and the final XML-escaped provider prompt to 64 KiB. Supported memory writes and restore cap a source record at 256 KiB plus a 4 KiB title. The Memory library itself returns immutable 16-item keyset pages, computes visible document chunk counts with `fetchCount`, and pages the conversation picker rather than retaining the full memory, document, chunk, or conversation tables on the UI actor. A document deletion takes an exclusive source lease, stages its chunk cascade with autosave disabled, preserves cancellation until the explicit commit boundary, and removes only matching rebuildable vectors in bounded UUID pages. A saved context receipt is verified only when its sheet is requested. Store-generation and request-identity tokens clear or disable old transcript, receipt, curated-memory, sidebar, and destructive-action state until the replacement generation has been read back; constant-time revision tokens invalidate other bounded root reads without hashing every record.

Conversation deletion owns an exclusive source-operation lease. Before that lease is reserved, the same main-actor turn commits any pending draft/source edits through the normal gate; a failed flush or active operation prevents deletion from starting. The deletion actor disables its private context's autosave before staging the complete source cascade, including the automatic-memory reconciliation described above, so cancellation remains real until the one explicit destructive commit boundary. After that boundary it finishes exactly and publishes one bounded root revision. Rebuildable conversation-message and learned-topic vectors are then removed on their own model actor with cache-key pages and source-kind isolation, so neither a large chat nor the vector table is materialized on the UI actor. A cache-cleanup failure does not roll back an already verified source deletion because stale derived vectors are rejected during later retrieval.

If SwiftData cannot open the source store, the app still renders a standalone recovery view instead of terminating or silently substituting an in-memory store. It states that existing data was not deleted or replaced, offers Retry plus portable-backup recovery, and keeps sanitized technical diagnostics behind progressive disclosure. Launch recovery validates the selected backup independently, restores it into a fresh UUID-named store generation, verifies exact read-back, and only then atomically updates a small `ActiveStore.json` pointer. A process-wide lease covers staging, pointer activation, cache cleanup, and the app transition, so the macOS main window and Settings cannot race two selected backups. A failed pre-activation attempt removes only the unique generation directory it created; a partial pointer commit is detected and retains the selected generation. The failed SQLite/WAL family is never moved, truncated, or deleted; an invalid backup or interrupted pre-selection attempt leaves it selected and untouched. `MosaicRootView` and Settings are instantiated only after a real container opens; the Mac New Chat command is disabled in recovery state. The rebuildable semantic vector index is cleared best-effort after a successful generation switch and revalidated before later use.

## Scheduling policy

Foreground execution is app-scoped: each activation starts a lightweight 30-second due-task sweep, so prompts can run while the user is chatting without opening Automations. Scene changes stop the loop only between tasks; an already opened paid provider stream owns its lifecycle and finishes terminal persistence instead of being cancelled by navigation or temporary inactivity. The shared runner synchronously reserves Run Now, persists an execution claim before awaiting the provider, creates a conversation, captures curated/semantic/project context, and revalidates every source boundary immediately before streaming. A successful result records actually used memory topics and enqueues the same isolated automatic-memory formation path as an interactive reply, then advances the next run according to the recurrence and stored time zone. This prevents double taps and a terminated one-time run from being charged again automatically; recurring failures remain visible and continue at their next scheduled occurrence.

When notification permission is already granted, a local one-shot calendar notification is scheduled for each task's exact `nextRunAt`. Deterministic per-task identifiers let create, edit, pause, resume, run, delete, restore, launch, and sweep reconciliation replace or remove stale reminders without duplicates; completion notifications use a separate identifier namespace. Notification-center mutations pass through a cancellation-aware serial gate, so an older suspended add cannot land after a newer pause, edit, deletion, or full reconciliation. A store-generation change also triggers immediate reminder-only reconciliation, independently of the 30-second provider-work sweep. Reconciliation never prompts for permission. Only the visible user action requests it, and retained app delegates present permitted reminder banners, lists, and sounds while the app is foregrounded.

iOS background scheduling is intentionally not treated as exact execution. If the app is suspended or terminated, the due-time notification asks the user to reopen the app and the local runner executes at the next foreground opportunity. A later reliable background or cloud runner is a separate deployment and privacy decision, not a hidden implementation detail.

### Personal events and model selection (V5)

Automatic-memory prompt v4 distinguishes lasting information from user-reported personal events. Events require at least 0.75 confidence and evolving stability; they preserve the source user message’s date in `lastConfirmedAt`, including delayed formation, without inventing an occurrence date or inferring ownership. Older reports cannot replace a newer resolution. A resumed job uses its originally recorded model; prompt upgrades explicitly retire superseded pending jobs instead of retrying an obsolete job indefinitely.

`RecentEventMemoryPolicy` applies a 45-day ranking half-life with a 0.4 floor and shields events that already rank in the top three results at 0.85 (`EventFadePolicy.standard`, selected on held-out personas of the synthetic memory benchmark; the earlier 14-day/0.15 policy made month-old events nearly unrecallable); the Memory UI distinguishes recent (30 days) and past events without deleting either. External retrieval includes at most two learned events inside the existing six-item/8,000-character budget and renders report-date/historical-use guidance separately from canonical topic text. This preserves candidate fingerprints, backup evidence and source revalidation. `MemoryRecallQuery` appends at most two 450-character recent user turns only to short referential questions; assistant replies never provide that query context.

`ProviderModelStore` is the shared resolver for conversation sends, task runs and resumed memory jobs. Chat/task pickers list only enabled models from enabled chat-capable providers; exact selected-model limits and request provenance travel with the immutable connection snapshot. Disabling a selected model surfaces an explicit choice requirement, without silently switching providers or rewriting history. Embedding profiles and Gemini Live remain separate input/retrieval features.

### Rendering and local recall limitations

Message bubble rounding belongs to the user bubble's background shape. Do not clip the whole message stack: assistant messages have no bubble padding, so a rounded mask cuts the first glyph and the provenance tile even when the row fits inside the transcript.

The local retrieval fallback normalizes Turkish spelling and compares lexical tokens and hashed character features; it is not a multilingual semantic model. A translated memory or a category-level question may have no matching words and yield zero recalled items despite an enabled global memory. Switching the chat generation model does not change this local selection stage. Semantic matching uses separately enabled embedding profiles and the existing scope, revalidation, and context-budget limits. Do not silently enable a remote profile or solve a recall miss by injecting the entire memory library.

### Multiline message drafts

Do not collapse the composer to a one-line TextField when keyboard avoidance reduces the viewport: it makes long drafts scroll horizontally. The composer uses a native TextEditor with an invisible wrapping Text to supply natural height; the editor is an overlay, so it cannot expand to consume the whole transcript. A viewport-relative height cap enables native vertical scrolling. Both layers use the same body font and text-container padding; a measurement-only zero-width sentinel preserves the final empty line without entering the actual draft. Keep editing bound to composerText so autosave and finalized/interim transcription behavior remain intact. Return is a newline; sending is explicit (button or Command-Return).

Keep vertical fixed sizing both before and after the maximum-height frame: otherwise an empty editor can consume the cap instead of its natural one-line height. Do not imperatively scroll the transcript on viewport-height changes or content-height changes while the composer is focused. Growing drafts plus those scroll requests caused a SwiftUI layout/scroll commit loop and a frozen app; native bottom anchoring handles viewport resizing. The Latest button is an overlay so its appearance does not change transcript height.
