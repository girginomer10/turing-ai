# Benchmarks

Evaluation work behind Turing AI's retrieval and memory layers. Every benchmark drives the shipped code (the Swift `HybridMemoryRetriever`, the app's Smart memory prompt and decoder, the automatic-memory validator) rather than a re-implementation, and reports bootstrap confidence intervals. Where a configuration is chosen, it is chosen on DEV data and reported on disjoint TEST data.

**Report:** [Evidence-Driven Memory Retrieval for a Multilingual, Provider-Agnostic AI Client](report/Turing-AI-retrieval-report.pdf) (8 pages) · [two-page summary](report/Turing-AI-retrieval-summary.pdf)

## Running

Each directory's README lists its prerequisites and exact commands. In short:

- Local models run through llama.cpp from GGUF files; hosted models read their keys from `benchmarks/.env`, which is git-ignored. `python3 common/check_keys.py` sends one tiny request per configured key and never prints a key.
- Every hosted call is charged to a local spend ledger with a per-provider cap, so a run cannot overspend silently.
- The fictional memory and verifier datasets are committed under their `data/` directories. XQuAD is downloaded and the agent's worlds are generated by their pipelines. Raw intermediate outputs go to `work/`, which is git-ignored and rebuilt by re-running the pipeline.

All personas, conversations and worlds in these benchmarks are fictional.
